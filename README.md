# StrictQL

**StrictQL** is a single-file, multi-writer relational database written in [Stricta](https://github.com/lucianmarin/stricta). It combines **SQLite's single-file, zero-setup simplicity** with **PostgreSQL's SQL dialect, MVCC semantics, and v3 wire protocol**, allowing developers and frameworks like **Django ORM** (`django.db.backends.postgresql` / `psycopg`) to use StrictQL as a drop-in replacement for PostgreSQL without managing a separate database server.

---

## Philosophy

- **Single-File Simplicity**: A database is a single `.sqlit` / `.strictql` file (plus an automatic sidecar `-wal` / `-shm` during active multi-writer sessions). No daemon, no cluster config, no external server setup.
- **Multi-Writer Concurrency**: Unlike SQLite (which serializes writers even in WAL mode), StrictQL uses **MVCC + Optimistic Concurrency Control (OCC)** over `mmap` shared memory, LLVM `atomic_*` primitives, and append-only WAL frames so multiple threads and processes can write concurrently.
- **PostgreSQL Interface**: Speaks the **PostgreSQL SQL dialect** and **PostgreSQL v3 wire protocol** (over Unix domain socket or localhost TCP), so standard PostgreSQL drivers (`psycopg`, `psql`, Django ORM) work out of the box.
- **Native Speed & Memory Safety**: Compiled to native machine code via Stricta + LLVM IR (`clang -O2`) with zero GC or runtime overhead.

## Architecture

```
  Django ORM / psycopg / psql / Stricta App
                    │
        ┌───────────┴───────────┐
        │   PG v3 Wire Server   │  (Unix socket / TCP, optional embedded API)
        └───────────┬───────────┘
                    │
        ┌───────────┴───────────┐
        │   PostgreSQL Dialect  │  Lexer, Parser, Planner, Executor
        │    (sql.str /         │  RETURNING, ON CONFLICT, ILIKE, $1,
        │     engine.str)       │  SERIAL/IDENTITY, pg_catalog
        └───────────┬───────────┘
                    │
        ┌───────────┴───────────┐
        │   MVCC + WAL Storage  │  Single-file paged store, atomic txid,
        │    (storage.str)      │  mmap shared state, flock checkpointing
        └───────────────────────┘
```

### 1. Storage Engine (`storage.str`)
- **Single-file persistence**: Self-contained database file with header magic (`STRQL001`), schema catalog, and append-only WAL frames (`<db>.wal`) for crash-safe durability.
- **MVCC & Multi-Writer**:
  - Each transaction receives a monotonic `txid` via `atomic_add` on `mmap`-backed shared state (`multiprocessing.SharedMemory`).
  - Readers see a consistent snapshot without blocking writers; writers buffer mutations and commit atomically via WAL append + `FileLock` coordination.
  - Checkpointing compacts WAL frames back into the main database file.

### 2. PostgreSQL SQL Dialect (`sql.str`, `engine.str`)
- **Data Types**: `BIGINT`/`INT`/`INTEGER`, `DOUBLE PRECISION`/`FLOAT`/`NUMERIC`, `TEXT`/`VARCHAR`, `BOOLEAN`/`BOOL`, `BYTEA`, `TIMESTAMPTZ`/`TIMESTAMP`, `DATE`, `UUID`, `JSONB`.
- **DDL**: `CREATE TABLE [IF NOT EXISTS]`, `DROP TABLE [IF EXISTS]`, `PRIMARY KEY`, `SERIAL` / `BIGSERIAL` / `GENERATED BY DEFAULT AS IDENTITY`, `NOT NULL`, `DEFAULT`, `UNIQUE`.
- **DML**:
  - `INSERT INTO ... (...) VALUES (...) [RETURNING ...]`
  - `ON CONFLICT (...) DO NOTHING | DO UPDATE SET ...`
  - `SELECT ... FROM ... [WHERE ...] [ORDER BY ...] [LIMIT ...] [OFFSET ...]`
  - `UPDATE ... SET ... [WHERE ...] [RETURNING ...]`
  - `DELETE FROM ... [WHERE ...] [RETURNING ...]`
- **Expressions & Operators**: `=`, `!=`/`<>`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, `NOT`, `IS NULL`, `IS NOT NULL`, `LIKE`, `ILIKE`, `IN (...)`, `$1, $2` parameter placeholders, double-quoted `"identifiers"`.
- **Transactions**: `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`.
- **Catalogs**: Minimal `pg_catalog` / `information_schema` support for ORM migrations and introspection.

### 3. PostgreSQL v3 Wire Protocol (`pgwire.str`)
- Supports `StartupMessage`, `SSLRequest` (cleanly declined with `'N'`), `AuthenticationOk`, `ParameterStatus`, `BackendKeyData`, `ReadyForQuery`.
- Simple Query (`'Q'`) and Extended Query (`Parse`, `Bind`, `Describe`, `Execute`, `Sync`) with `RowDescription`, `DataRow`, `CommandComplete`, `ErrorResponse`, and `Terminate` (`'X'`).

## Quick Start

### Prerequisites
Install [Stricta](https://github.com/lucianmarin/stricta) and [fetch](https://github.com/lucianmarin/fetch) via Homebrew:
```bash
brew tap lucianmarin/tap
brew install --HEAD stricta
brew install --HEAD fetch
```

### Install Dependencies, Build & Setup
```bash
fetch install
fetch build main.str -o strictql
```

Run a single database over TCP or Unix socket:
```bash
./strictql mydb.strictql --port 5432
./strictql mydb.strictql --socket /tmp/.s.PGSQL.5432
```

Or serve multiple databases from a single process (routes each connection's `database` parameter to `<dir>/<dbname>.strictql` with an independent `RWLock` per database):
```bash
./strictql --dir /var/lib/strictql --port 5432
./strictql --dir /var/lib/strictql --socket /tmp/.s.PGSQL.5432
```

- `--port <port>`: Listen on localhost TCP port (default: `5432`).
- `--socket <path>`: Listen on a Unix domain socket (e.g. `/tmp/.s.PGSQL.5432` for `psycopg2`/`asyncpg`/Django).
- `--dir <path>`: Multi-database directory mode — lazily opens `<path>/<dbname>.strictql` per requested database name.

### Run Tests
```bash
make test
```

### Embedded Usage in Stricta
```python
import engine

db = engine.open("app.strictql")
db.execute("CREATE TABLE users (id SERIAL PRIMARY KEY, name TEXT NOT NULL)")
res = db.execute("INSERT INTO users (name) VALUES ('Alice') RETURNING id, name")
print(res.rows)
db.close()
```

## Benchmarks

Benchmarked against real `../news` queries (`articles` schema & 200 real rows) comparing in-process SQLite (`aiosqlite`), PostgreSQL 18 (`asyncpg` over Unix socket), and in-process embedded StrictQL:

| Benchmark (ms) | SQLite (emb) | Postgres 18 (unix) | StrictQL (emb) | vs Postgres 18 | vs SQLite |
|---|---:|---:|---:|---|---|
| `insert_200` (200 inserts, transactional) | 6.48 | 8.51 | **2.20** | **3.87× faster** | **2.95× faster** |
| `homepage_10x` (10× `ORDER BY` + `IN`) | 2.33 | 2.99 | **1.26** | **2.37× faster** | **1.85× faster** |
| `count_10x` (10× indexed `COUNT(*)`) | 0.64 | 0.67 | **0.19** | **3.53× faster** | **3.37× faster** |
| `distinct_10x` (10× `SELECT DISTINCT`) | 0.74 | 1.23 | **0.12** | **10.25× faster** | **6.17× faster** |
| `search_10x` (10× `ILIKE '%ai%'`) | 0.85 | 0.76 | **0.66** | **1.15× faster** | **1.29× faster** |
| **TOTAL** | **11.04** | **14.16** | **4.44** | **3.19× faster** | **2.49× faster** |

### 500 Concurrent Users (`../subreply`, sync `psycopg2`)

Benchmarked against `../subreply` multi-table relational queries (`app_user`, `app_post`, `app_bond` with `INNER JOIN` + `IN (SELECT ...)` subqueries) using 500 concurrent `psycopg2` threads over Unix sockets:
- **PostgreSQL 18 (default settings, `max_connections=100`)** behind **PgBouncer** (`pool_mode = transaction`, `default_pool_size = 90`, `max_client_conn = 600`).
- **StrictQL** serving all **500 simultaneous direct connections** over a Unix socket (no connection pooler required).

| 500-User Sync `psycopg2` (ms) | PG 18 + PgBouncer | StrictQL (500 conns) | Speedup |
|---|---:|---:|---:|
| `500_writes_1500` (500 writers × 3 inserts) | 34.34 | **20.94** | **1.64× faster** |
| `500_reads` (500 `FeedResource` `JOIN`s) | 24.68 | **18.48** | **1.34× faster** |
| `500_mixed` (500 simultaneous write + feed read) | 30.91 | **19.57** | **1.58× faster** |
| **TOTAL** | **89.93** | **59.00** | **1.52× faster** |
